# AGENTS.md

## Architecture & Stack

### Tech Stack

* **Frontend**: Svelte 5, TypeScript, Vite, Tailwind 4, Bits UI, Shadcn-Svelte, Lucide-Svelte
* **Backend**: Tauri 2 (Rust), SQLite (SQLx)
* **Tauri Plugins**: clipboard-manager, dialog, log, notification, opener, process, single-instance, store, window-state

### Structure

* `.github/` - GitHub Actions workflows
* `src/components/` - Shared UI components
* `src/features/` - Feature modules (components, hooks, store)
* `src/lib/` - Utilities, config, constants
* `src/stores/` - Global Svelte stores (Runes)
* `src-tauri/` - Rust backend

### Type Generation (Specta)

* **Source**: Tauri commands annotated with `#[specta::specta]` and types deriving `Type`.
* **Collection**: `src-tauri/src/api.rs` gathers all commands/types into a builder.
* **Output**: `src/bindings.ts`. This is auto-generated on the `check:frontend` and test commands.

## Coding Standards

### 🚨 Critical Rules

1. **No Placeholders**: Never leave TODOs, stubs, or "exercise for the user". Write full, working code.
2. **Bindings**: NEVER manually edit `src/bindings.ts`. It is auto-generated by Specta.
3. **Protected Files**: NEVER modify components within `src/components/ui/*`. You are free to add and remove components via the CLI.
4. **Logging**: NEVER use `println!` or `eprintln!` directly in the backend code (outside the CLI crate). Use standard Rust `log` macros (`log::info!`, `log::error!`, etc.) exclusively so that output is correctly routed through the `tauri-plugin-log` infrastructure for users and persisted to disk.

### 🧠 General Philosophy

* **Production Ready**: No half-measures. Code must be clean, robust, and handle edge cases.
* **Engineering Principles**: Adhere to SRP, DRY, and YAGNI.
* **Complexity**: Do not introduce abstractions unless explicitly required.
* **Documentation**: Document *why* complex logic exists, not *what* the code is doing.

### TypeScript / Frontend

* **Strict Mode**: No `any` types. EVER.
* **Internationalization (i18n)**: Hardcoded user-facing text in Svelte templates is strictly forbidden. Always add new strings to `src/locales/en.json` (and `es.json`) and use the `t()` function from `src/lib/i18n` for rendering text. Do not forget to update the other locales when adding new strings.
* **Async & Error Handling**: Always use the `executeSafeAction` wrapper from `src/lib/async-utils.ts` for IPC calls and asynchronous frontend operations. Do not clutter components with boilerplate `try/catch` blocks and manual toast implementations.
* **Comments**: 
  * 🚫 **Banned**: Conversational/History comments (e.g., `// updated import`, `// fixed x`, `// removed y`).
  * ✅ **Allowed**: Explanations of complex business logic or edge cases.
* **Styling**: Use `cn()` for conditional classes. Follow existing Shadcn patterns.
* **Animations**: All animations must use standardized durations.
  * **Snappy (150ms)**: Micro-interactions (hovers, sidebar collapse).
  * **Normal (200ms)**: Large transitions (sheets, dialogs).
  * **Implementation**: Use CSS variables `var(--duration-snappy)` / `var(--duration-normal)` or Tailwind classes `duration-150` / `duration-200`.
* **Imports**: Use `@/` alias for root.

### Rust / Backend

* **Command Registration**: Whenever a new `#[tauri::command]` is created, it MUST be manually added to the `collect_commands!` macro inside `src-tauri/src/api.rs` to expose it to the TypeScript bindings.
* **Error Handling**: NEVER use `.unwrap()` or `.expect()` outside of initial application setup. All Tauri commands must return the custom `CResult<T>` type defined in `error.rs` to gracefully propagate errors.
* **Architecture**: Keep `command.rs` thin. Route all business logic through the modules in `src/services/`.
* **CLI/GUI Parity**: Business logic lives in `services/`. Tauri commands in `command.rs` are thin async wrappers, and CLI methods in `cli.rs` delegate to the same service functions via `block_on`. Never duplicate business logic between the two; extract shared code into a service function (e.g., `job_service::spawn_download_job`).

### 🧪 Testing Strategy & Execution

> **Philosophy:** We don't need 100% test coverage, but the critical stuff *must* work. Focus testing efforts on business logic, state management (stores), and core user journeys. All UI components handling state, IPC calls, or complex logic must be tested.

**🚨 Mandatory Rule:** You MUST write a corresponding Vitest or Cargo test whenever you create or modify a service or store. This is non-negotiable.

#### 1. E2E Testing (Playwright)

* **Requirement:** Any new user journey, feature module, or Settings tab modification requires a new or updated E2E Playwright test injected with the mock backend.
* **The Golden Rule:** Never test the real Tauri backend in E2E unless explicitly required. Always inject the mock IPC layer (as seen in `e2e/flow.spec.ts`) to keep tests fast, deterministic, and isolated.
* **Zero-Guessing Policy:** Do NOT attempt to blindly guess DOM selectors for new tests.
* **The Flow:** When a new E2E test is needed, you must FIRST outline the exact click-path and actions the user should take in the UI. Then, instruct them to run `pnpm exec playwright codegen http://localhost:1420`, perform those outlined actions, and paste the generated code back to you.
* **Implementation:** Once the user provides the raw code, refine it by:
  1. Swapping brittle locators for resilient ones (prefer `getByRole`, `getByText`, etc.).
  2. Injecting the mock backend IPC layer to intercept Tauri commands.
  3. Adding robust assertions and cleaning up the flow.

#### 2. Frontend Unit/Component Tests (Vitest)

* **Target:** Global Svelte stores (`src/stores/*.svelte.ts`) and complex utility functions (`src/lib/*.ts`).
* **Mocking**: 
  * **Tauri IPC**: You MUST use the official `mockIPC` from `@tauri-apps/api/mocks`. NEVER use `vi.mock` for `@tauri-apps/api` or `@tauri-apps/plugin-*` imports as manual mocks fail to preserve the full API surface and cause non-deterministic behavior.
  * **External Libs**: Use Vitest's `vi.mock()` to stub out non-Tauri dependencies so tests run seamlessly in Node/Happy-DOM.
* **Command**: Run tests via `pnpm test:frontend`.

#### 3. Backend Unit Tests (Rust)

* **Target:** The `src/services/` layer. This is where the actual heavy lifting and business logic lives.
* **Skip:** Do not waste time testing the thin wrappers in `command.rs` or `cli.rs` unless they contain specific, non-trivial routing logic.
* **Command:** Run tests via `pnpm test:backend`.

### Quality Checks

🚨 **CRITICAL RULE:** Do NOT run individual test commands directly (e.g., `pnpm test:frontend`, `pnpm test:backend`, `pnpm test:vitest`) to verify changes. You MUST exclusively use `pnpm verify` as it orchestrates all test suites, lints, and type checks correctly and guarantees overall safety.

You cannot say you have finished until you have run `pnpm verify` and it passes with **an exit code of 0**.
Do NOT run `pnpm verify` if your changes are strictly limited to purely documentation (`.md`) or configuration files that are not validated by `scripts/verify.js` (such as workflow files or locale files). However, you MUST run `pnpm verify` if you modified any code files or key configuration files checked by `scripts/verify.js` (e.g., `package.json`, `tsconfig*`, `vite.config.ts`, `cargo.toml`, etc.).

### 📦 Dependency Management

Never specify version numbers in your commands to make sure `pnpm` and `cargo` grab the latest versions.

* **Frontend**: Use `pnpm`. When adding, always use `-D` since this is a Tauri application.
* **Backend**: Use `cargo`. Then reorganize the entry into the correct category section in `Cargo.toml`.

### 🧱 UI Components (Shadcn)

### Linux Notifications & D-Bus Conflicts

*   **Issue**: On some Linux environments (specifically those with libayatana-appindicator or certain desktop managers), the standard `tauri-plugin-notification` may fail to show OS notifications despite having correct permissions.
*   **Workaround**: Use a "Dual Dispatch" strategy in the backend. Attempt to show the notification via the standard plugin FIRST, then immediately fire a fallback command using `notify-send`. This ensures that if D-Bus communication is blocked or conflicted, the shell fallback still delivers the message.
*   **Dependency**: Keep `tauri-plugin-notification` for cross-platform support but ensure `notify-send` is available on the host system.

### Playwright Actionability & UI Interactions

*   **Issue**: Using `page.evaluate(() => el.click())` or `.evaluate((btn) => btn.click())` in Playwright bypasses the framework's built-in actionability checks (visibility, stability, and occlusion). This can lead to false positives where tests pass even if a button is physically covered by another element (e.g., a modal or toast) in production.
*   **Fix**: Always prefer standard Playwright action methods like `.click()`, `.fill()`, or `.check()`. Only use `evaluate` for non-interactive DOM manipulation or data extraction.

### Global Vitest Teardown & Svelte 5 Lifecycle

*   **Issue**: `AbortError` or `DOMException` occurs during component unmount in Vitest + Happy DOM when using fake timers and bits-ui components.
*   **Fix**: In the global `afterEach` hook, always call `cleanup()` (from `@testing-library/svelte`) **BEFORE** flushing fake timers (e.g., `vi.runAllTimers()`). This allows Svelte's asynchronous transition microtasks to settle before the timers are advanced, preventing crashes in the reactive environment.

### E2E State

*   **Issue**: Never expose internal stores to the `window` object for testing. Use native DOM events or Playwright's `context` APIs to trigger state changes, ensuring the test mimics real user/browser behavior.
