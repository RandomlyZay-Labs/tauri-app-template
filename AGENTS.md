# AGENTS.md

## Architecture & Stack

### Tech Stack

* **Frontend**: Svelte 5, TypeScript, Vite, Tailwind 4, Bits UI, Shadcn-Svelte, Lucide-Svelte
* **Backend**: Tauri 2 (Rust), SQLite (SQLx)
* **Tauri Plugins**: clipboard-manager, dialog, log, notification, opener, process, single-instance, store, window-state

### Structure

* `.github/` - GitHub Actions workflows
* `src/components/` - Shared UI components
* `src/features/` - Feature modules (components, hooks, store)
* `src/lib/` - Utilities, config, constants
* `src/stores/` - Global Svelte stores (Runes)
* `src-tauri/` - Rust backend

### Type Generation (Specta)

* **Source**: Tauri commands annotated with `#[specta::specta]`, types derive `Type`.
* **Collection**: `src-tauri/src/api.rs` gather commands/types to builder.
* **Output**: `src/bindings.ts`. Auto-generated on `check:frontend` + test commands.

## Coding Standards

### 🚨 Critical Rules

1. **No Placeholders**: No TODOs, stubs, "exercise for user". Write full, working code.
2. **Bindings**: NEVER manually edit `src/bindings.ts`. Auto-generated by Specta.
3. **Protected Files**: NEVER modify components in `src/components/ui/*` unless file listed in `AGENTS.md` under **Modified UI Components** list. Modified `src/components/ui` files must be listed with reasoning.
4. **Logging**: NEVER use `println!` or `eprintln!` in backend code (outside CLI crate). Use Rust `log` macros (`log::info!`, `log::error!`, etc.) to route output to `tauri-plugin-log` + disk.

### 🧠 General Philosophy

* **Production Ready**: No half-measures. Clean, robust code, handle edge cases.
* **Engineering Principles**: Adhere to SRP, DRY, YAGNI.
* **Complexity**: No abstractions unless required.
* **Documentation**: Document *why* complex logic exists, not *what* code does.

### TypeScript / Frontend

* **Strict Mode**: No `any` types. EVER.
* **Internationalization (i18n)**: No hardcoded text in Svelte templates. Add strings to `src/locales/en.json` + `es.json`. Use `t()` from `src/lib/i18n` to render. Update other locales when adding strings.
* **Async & Error Handling**: Use `executeSafeAction` wrapper from `src/lib/async-utils.ts` for IPC + async frontend operations. No boilerplate `try/catch` or manual toasts in components.
* **Comments**: 
  * 🚫 **Banned**: Conversational/History comments (`// updated import`, `// fixed x`, `// removed y`).
  * ✅ **Allowed**: Explanations of complex business logic / edge cases.
* **Styling**: Use `cn()` for conditional classes. Follow Shadcn patterns.
* **Animations**: Standard durations:
  * **Snappy (150ms)**: Micro-interactions (hovers, sidebar collapse).
  * **Normal (200ms)**: Large transitions (sheets, dialogs).
  * **Implementation**: Use CSS variables `var(--duration-snappy)` / `var(--duration-normal)` or Tailwind classes `duration-150` / `duration-200`.
* **Imports**: Use `@/` alias for root.

### Rust / Backend

* **Command Registration**: New `#[tauri::command]` must be added to `collect_commands!` macro in `src-tauri/src/api.rs` to expose to TS bindings.
* **Error Handling**: NEVER use `.unwrap()` or `.expect()` outside initial setup. Tauri commands must return custom `CResult<T>` defined in `error.rs` to propagate errors.
* **Architecture**: Thin `command.rs`. Route business logic through modules in `src/services/`.
* **CLI/GUI Parity**: Business logic in `services/`. Tauri commands in `command.rs` are thin async wrappers. CLI in `cli.rs` delegates to service functions via `block_on`. Do not duplicate business logic. Extract to service function (e.g. `job_service::spawn_download_job`).

## Workflow & Commands

### 🧠 Agent Protocol

1. **Debug Lifecycle**: Keep debugging code until issue resolved.
2. **Leave No Trace**: Append critical lessons to Lessons section at end.

### 🧪 Testing Strategy & Execution

> **Philosophy:** No 100% test coverage needed. Critical code must work. Focus on business logic, stores, core user journeys. Test UI components handling state, IPC, complex logic.
**🚨 Mandatory Rule:** Write Vitest or Cargo test when creating/modifying service or store. Non-negotiable.

#### 1. E2E Testing (Playwright)

* **Requirement:** New user journeys, feature modules, Settings tab changes need new/updated E2E Playwright tests with mock backend.
* **The Golden Rule:** Do not test real Tauri backend in E2E unless required. Inject mock IPC layer (`e2e/flow.spec.ts`) for fast, isolated tests.
* **Zero-Guessing Policy:** Do not guess DOM selectors.
* **The Flow:** Outline click-path/actions. Ask user to run `pnpm exec playwright codegen http://localhost:1420`, perform actions, paste code back.
* **Implementation:** Refine user code:
  1. Swap brittle locators for resilient ones (prefer `getByRole`, `getByText`, etc.).
  2. Inject mock backend IPC layer to intercept Tauri commands.
  3. Add assertions, clean flow.

#### 2. Frontend Unit/Component Tests (Vitest)

* **Target:** Global Svelte stores (`src/stores/*.svelte.ts`) + complex utility functions (`src/lib/*.ts`).
* **Mocking**: 
  * **Tauri IPC**: Use official `mockIPC` from `@tauri-apps/api/mocks`. NEVER use `vi.mock` for `@tauri-apps/api` or `@tauri-apps/plugin-*` imports (manual mocks fail to preserve API surface, cause flakiness).
  * **External Libs**: Use Vitest `vi.mock()` to stub non-Tauri dependencies for Node/Happy-DOM.
* **Command**: Run tests via `pnpm test:frontend`.

#### 3. Backend Unit Tests (Rust)

* **Target:** `src/services/` layer (heavy lifting, business logic).
* **Skip:** Do not test thin wrappers in `command.rs` or `cli.rs` unless routing logic non-trivial.
* **Command**: Run tests via `pnpm test:backend`.

### Quality Checks

🚨 **CRITICAL RULE:** Do NOT run individual test commands (`pnpm test:frontend`, `pnpm test:backend`, `pnpm test:vitest`) directly. Use `pnpm verify` to run all test suites, lints, type checks.
Must run `pnpm verify` and pass with exit code 0 to finish.
Skip `pnpm verify` if changes are documentation (`.md`) or configuration not validated by `scripts/verify.js` (workflows, locales). Run `pnpm verify` if modified code files or key configs checked by `scripts/verify.js` (`package.json`, `tsconfig*`, `vite.config.ts`, `cargo.toml`).

### Linux Notifications & D-Bus Conflicts

*   **Issue**: `tauri-plugin-notification` fails on some Linux environments (libayatana-appindicator/desktop managers) despite permissions.
*   **Workaround**: Dual Dispatch in backend. Try standard plugin FIRST, then fallback to `notify-send`. Ensures delivery if D-Bus blocked.
*   **Dependency**: Keep `tauri-plugin-notification` for cross-platform. Ensure `notify-send` on host.

### Playwright Actionability & UI Interactions

*   **Issue**: `page.evaluate(() => el.click())` or `.evaluate((btn) => btn.click())` bypasses actionability checks (visibility, stability, occlusion). Can cause false positive passes when button is covered in prod.
*   **Fix**: Prefer Playwright actions `.click()`, `.fill()`, `.check()`. Use `evaluate` only for non-interactive DOM manipulation/data extraction.

### Global Vitest Teardown & Svelte 5 Lifecycle

*   **Issue**: `AbortError`/`DOMException` on component unmount in Vitest + Happy DOM with fake timers + bits-ui.
*   **Fix**: In global `afterEach`, call `cleanup()` (from `@testing-library/svelte`) BEFORE flushing fake timers (`vi.runAllTimers()`). Let Svelte transition microtasks settle before advancing timers, preventing crashes.

### E2E State

*   **Issue**: Do not expose internal stores to `window` for testing. Use native DOM events or Playwright `context` APIs to trigger state changes to mimic user behavior.

### Sonner / svelte-sonner Stacking & Spacing in Production

*   **Issue**: Stacked toasts have much larger gaps or display as vertical lists in production, but behave correctly in development.
*   **Fix**: Never override `position: relative;` globally on `[data-sonner-toast]` (e.g. in `index.css`). The library relies on absolute positioning for stacking calculations. In production, global CSS specificity can override the library's dynamic positioning styles, preventing them from stacking properly.
